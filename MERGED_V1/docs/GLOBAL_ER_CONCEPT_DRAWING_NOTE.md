# 全局简洁概念 ER 图说明

## 1. 图的定位

本图用于课堂汇报中“需求分析 → ER 设计”这一页，采用 **Chen 概念 ER 图**：矩形表示现实实体，菱形表示现实联系。它刻意不展示字段、主键、外键、数据类型、索引和数据库工程表；这些内容应留到后续关系模式与物理数据库设计部分再讲。

这不是 47 张表的缩略图，而是从当前真实项目模型抽取出的“物业世界里有哪些对象、为什么会发生联系”。

## 2. 只读核对后的取舍

### A. 本图保留的实体（12 个）

- 小区、楼栋、单元、房产、户型模板：构成多小区物业的空间资产主骨架。
- 人员：承载业主、住户、缴费人和车辆登记人等现实角色。
- 仪表、账单、缴费记录、费用类型：说明收费不是单一字段，而是独立的计量和财务事实链。
- 车辆、车位：以轻量分支体现停车业务的现实对象。

### B. 本图保留的关系（14 个）

- 小区—包含—楼栋—包含—单元—包含—房产
- 房产—采用—户型模板
- 人员—拥有—房产
- 人员—居住—房产
- 人员—授权—房产
- 房产—配置—仪表
- 房产—生成—账单
- 账单—包含—费用类型
- 人员—支付—缴费记录—对应—账单
- 人员—登记—车辆
- 人员—使用—车位

### C. 本图故意省略的内容

- `ownership`、`residence`、`authorization`：数据库中是带日期、状态和附加信息的关联表；在概念 ER 中还原为“拥有 / 居住 / 授权”三个菱形关系，更能说明现实语义。
- `bill_item`、`fee_standard`、`meter_reading`、车证申请/车证：它们是真实业务表，但进入主图会把“课堂第一张概念图”变成流程或逻辑表图，留给后续收费/停车子图展开。
- `agency`、租赁挂牌、合同、通知、居民异常、地图边界、设施：属于真实扩展业务，非本页必须解释的主骨架。
- 账户、角色、权限、Token、数据范围、文件、审计、Flyway：属于安全、运行或工程演进支撑，不是现实物业对象。

### D. 这样取舍的原因

房产是人员、空间、收费和停车的共同锚点；因此图以房产为视觉中心。空间层级解释“多小区”，三种人员—房产关系解释真实使用场景，收费链说明系统的业务深度，停车分支证明业务并非只停留在房屋信息登记。

## 3. 与真实数据库的对应说明

- 空间主线对应 `community`、`building`、`building_unit`、`property_unit`、`layout_template`。
- “拥有”“居住”“授权”分别对应 `ownership`、`residence`、`authorization` 的业务语义；后者在数据库中还关联中介机构等实现细节，本图不展开。
- 收费主线对应 `meter`、`bill`、`payment`、`fee_type`；账单明细、收费标准、抄表读数作为后续关系模式/子图的细节。
- 停车主线对应 `vehicle`、`parking_space` 和 `parking_right` 的概念语义。当前车证业务不绑定固定车位，因此这里仅表达“人员使用车位”的概念扩展，不宣称当前已有固定分配数据。

## 4. 适合放入 PPT 的位置

建议放在“需求分析完成后、关系模式设计之前”的单页：

```text

→ 主要使用者与核心业务

```

## 5. 课堂讲解提纲（约 60–90 秒）

1. “我们没有一开始就堆数据库表，而是先从现实物业对象抽象。”
2. “空间上，系统支持小区、楼栋、单元到房产的多层级管理，房产是业务交汇点。”
3. “人员与房产之间要区分拥有、居住和授权：业主不一定居住，住户也不一定拥有产权，因此不能合并为一个关系。”
4. “收费不是在房产上加一个金额字段，而是由仪表、账单、费用类型和缴费记录构成独立链条。”
5. “最后用车辆与车位展示系统还覆盖真实物业扩展业务；后续再把这些概念关系落到具体的表、主外键和约束中。”
