# 《多小区智慧物业管理系统》数据库课程设计报告 V2 半成稿

## 中文摘要

多小区物业管理同时涉及房屋空间层级、人员与房屋的时态关系、周期性收费、部分缴费、多社区管理权限以及持续变化的数据库结构。如果仅按页面制作若干增删改查表单，系统很容易把“当前状态”覆盖“历史事实”，把账单金额与付款金额混为一谈，或者让具有管理功能的账号越过其被授权的小区范围。针对这些问题，本课程设计以 MySQL 关系数据库为中心，设计了小区—楼栋—单元—房产的层级结构，将产权、居住、账单项目、付款、通知收件关系等独立建模，并使用主键、外键、唯一约束、CHECK、生成列、视图与事务维护数据的一致性。在访问层，Spring Boot 服务通过 MyBatis Mapper XML 组织分页、动态范围过滤、关联查询和聚合统计；在权限层，将“能执行某功能”与“能访问哪些小区的数据”分开判定。开发过程中，数据库结构从基础模型逐步扩展到文件元数据、多社区授权、车证和户型图变体；Flyway 记录了可见的 V1—V10 演进，同时最终数据库与这组脚本之间仍存在需要说明的来源缺口。项目利用结构化演示数据、约束负例、事务失败日志、执行计划和 Docker 数据卷恢复，对模型的可用性与边界进行了验证。报告重点讨论各项设计为何产生、如何进入真实查询与业务流程，以及其尚不能保证的性质。

**关键词：**关系数据库；多小区物业；完整性约束；MyBatis；数据作用域；数据库迁移；事务一致性

# 第一章 项目概述与开发环境

## 1.1 选题背景与课程设计价值

### 1.1.1 从单小区 CRUD 到多社区业务域

物业管理表面上有房产查询、人员登记、收费和通知等页面，但这些页面背后并不是互不相关的表。一个房产位于确定的小区、楼栋和单元；该房产在不同时间可以有不同的所有权和居住关系，可以配置水电等表计，按月形成账单，账单又分解为费用项目并被一次或多次付款结算。管理这些事实的人也不是简单地“已登录”或“未登录”：系统管理员与小区工作人员的权限不同，同为工作人员还可能分别负责一个或多个小区。关系的基数、时间性和作用域，使本题能够覆盖概念建模、范式、约束、查询优化和事务等数据库课程的核心内容。

以一套房的生命周期为例，空间定位首先经过 Community、Building、BuildingUnit 才到 PropertyUnit。登记住户时并不直接修改房产中的“当前住户姓名”，而是在 Person 与 PropertyUnit 之间增加带有起止时间的 Residence；出现产权变动时，由 Ownership 记录另一类关系。按账期生成 Bill 后，物业费、水费和电费等被分解为 BillItem，实收发生在 Payment；报表通过这些底层事实计算，而非保存一组与事实可能背离的“页面总数”。因此，一条业务链跨越多个实体，却保留了每个事实独立演进和核查的能力。

“多小区”也并非把 community 表插入四行即可成立。项目需要回答“哪个账号可以处理哪些小区的房产”，并在列表筛选、统计汇总以及按 ID 修改对象时保持同一答案。授课展示中，教师询问多小区如何体现，项目通过 account_community_scope 中同一账号对应多条授权记录、服务层作用域判定和最终 SQL 限定三个层次作答。这个问题成为本报告的主线之一：现实范围规则必须落实为关系记录和查询谓词，不能停留在菜单文案。

### 1.1.2 房产作为长期业务事实的锚点

本系统以 PropertyUnit 表示可独立管理的一套房，而不继续拆解到卧室 Room。这个粒度与产权登记、入住、挂牌、账单和户型图的共同业务对象一致，避免了“一个页面管理房屋、另一个页面管理房间”引起的引用歧义。房产并不是所有信息的容器：它保存标识、所在单元、面积和状态等自身属性，其他变化较频繁或具有历史意义的事实则通过外键与之关联。房屋长期存在，而住户可能搬入搬出、表计会持续产生读数、账单每月新增，所以核心对象稳定与关系事实可累积应同时满足。

最终部署前快照记录了 4 个小区、14 栋楼、40 个单元和 528 套房产；与其关联的还有 606 人、528 条产权关系和 597 条居住关系。计量部分有 1584 个表计和 15840 条读数，收费部分有 3696 张账单、18273 条账单项和 3324 条付款记录。528×3=1584、1584×10=15840、528×7=3696，显示这些数据带有规则化演示构造特征。它们不是独立随机行，而是沿房产、表计、账期等键相互关联，足以检验跨表 JOIN、分页及聚合；但它们不代表真实物业自然增长的数据分布，更不能据此宣称具有生产级大数据能力。

## 1.2 平台职责与数据流

### 1.2.1 关系数据库、业务服务和显式 SQL

Vue 页面负责展示和交互，不能成为数据真实性的来源。例如页面上的“共 528 套房”来自服务端分页响应中的 total，而不是页面把当前二十行乘以页数。HTTP 请求进入 Controller 后，Service 负责身份、业务条件、事务和对象范围判断；Mapper 接口将具体的数据访问操作交给 XML；MySQL 最终执行 JOIN、COUNT、SUM、过滤和排序。将复杂 SQL 放在 MyBatis XML 中，使课堂讨论可以从一个页面数字追到 Mapper 的语句、索引和底表，同时避免把规则散落在控制器或前端数组操作中。

项目存在两条需要区分的房产访问链：管理端的 /api/admin/properties 与较早的资产工作台 /api/v1/properties。两者服务的页面、Controller 和 Mapper 并不完全相同。正式报告以选定演示页面的真实请求为起点，不因为 URL 中都含 properties 就把不同链路混写。这个区分同时提示了接口演进的成本：新增管理端时，旧接口的授权边界必须重新检查，而非仅修改导航入口。

### 1.2.2 文件、部署与数据库版本的分工

关系表适合保存文件的业务归属、对象键、类型、散列值和状态，不适合将户型图二进制直接当作反复 JOIN 的业务列。因此 MySQL 的 file_object 等表记录可检索的元数据，MinIO 保存对象内容；下载和预览通过元数据定位对象。两种存储的优势不同，事务边界也不同：数据库事务不会自动覆盖 MinIO 操作，后文将讨论提交后删除旧对象和失败时补偿的设计。

Docker Compose 将 MySQL、Redis、MinIO、后端和前端放入可重复启动的运行环境；真正与数据库设计相关的是 named volume 和恢复验证，而不是“用了容器”这个标签。代码源文件可以交由 Git 管理，已经写入数据的 Schema 演变却需要另一条有顺序的版本历史，项目用 Flyway V1—V10 记录可见的迁移。最终部署库还包含迁移来源尚未定位的结构，所以“具备版本管理机制”与“任何新库均能仅凭当前十个脚本还原最终库”不能画等号。

## 1.3 研究方法与证据版本

### 1.3.1 事实基线、时间戳和非目标

报告采用五类证据：第一类是源码和 DDL，可证明规则如何定义；第二类是 2026-09-01 的 MySQL 最终备份，可证明当时的结构与行数；第三类是历史测试、日志和 Runbook，可证明特定时间的运行结果；第四类是根据这些材料作出的设计解释；第五类是尚未找到完整证据的陈述。不同证据不相互替代：源码中的表不意味着最终库有相应业务数据，某次测试 PASS 不意味着任何输入和环境下都不会失败，最终备份中的 DDL 也不能自动归因于某个较早的 Flyway 版本。

本设计着重研究关系模式、完整性、查询、范围控制、迁移与恢复。地图服务、前端组件、Redis 和公网演示被讨论，是因为它们把数据库数据投入运行或暴露出运维边界，不作为独立的数据库理论成果。报告中的“当前”若未特别说明，指上述最终备份与对应代码审计时点，不主张这是读者阅读报告当天的在线库状态。

# 第二章 需求分析与系统边界

## 2.1 参与者与权限需求

### 2.1.1 功能许可与对象范围是两个不同问题

系统管理员需要维护跨社区的资源和配置，物业工作人员处理被分配小区的房产、人员和收费，居民查看或发起与本人关联的业务，中介相关主体围绕挂牌授权执行有限操作。单纯定义“管理员可以查看房产”不足以表达管理范围：两个工作人员可能拥有相同的菜单许可，却只被分配不同的小区集合。需求因此分解为功能许可和数据范围两个维度。前者回答“是否可调用此类接口”，后者回答“该接口的哪几行记录、哪一个目标对象属于当前账号”。

对于列表查询，系统必须使数据库 WHERE 条件包含有效社区范围；对于根据 propertyId、billId 等主键执行的写入，不能相信客户端另传的 communityId，而要沿目标对象的真实外键反查归属社区。若只在菜单中隐藏“房产管理”，用户仍可能直接构造 HTTP 请求；若只过滤列表而忽略详情及修改，则知道 ID 的用户可能越界访问。因此需求从页面可见性延伸到每一条查询和状态变更路径。

### 2.1.2 居民与中介的业务边界

居民并不是“看不到管理员菜单的管理员”。其身份范围主要由本人 Person 及与房产的关系确定，办理入住、查看车证等接口必须以服务端身份查找其业务对象。中介或代理相关记录同样不等于拥有全小区数据访问权：挂牌授权、挂牌本身和正式合同代表不同阶段，不能因为中介曾参与一个申请，就自动获得该房产所有住户和账单信息。现有最终快照里若干合同类表为空，报告将它们列为已建模但非完整演示闭环的范围。

## 2.2 核心数据需求及生命周期

### 2.2.1 空间层级、人员与时态人房关系

系统需要稳定保存 Community、Building、BuildingUnit、PropertyUnit 的父子关系，并提供从房号反查小区、从小区统计房屋、从房产查询当前人员的路径。层级不能仅靠自由文本描述：如果每套房直接保存 community_name 和 building_name，楼栋更名需要修改大量房产行，也可能出现同栋房屋名称不一致。用逐级外键表达位置，使同一栋楼的房屋共享一条权威楼栋记录。

Person 是人的身份事实，Ownership 表示人与房屋之间的产权事实，Residence 表示居住事实。三者生命周期不同：一个人可以拥有但不居住，一套房也可以由非业主居住；搬出不应删除这个人，更不应删除产权。系统既要查“某房当前谁住”，也要查“过去住过谁”，故关系要携带开始、结束、当前状态等属性，并通过约束和事务维持有效区间。当前态查询是历史表上的有条件视图，而不是覆盖式的单个 resident_id 字段。

### 2.2.2 收费、计量和资金事实

收费需要保存可重复使用的 FeeType，以及在不同小区、不同生效日期适用的 FeeStandard。Bill 是某套房某账期的一次出账事实，BillItem 保存该账单中不同项目的数量、单价与金额。Payment 是资金发生事实，具有状态、金额与关联账单；一次付款可以小于账单应收，部分缴费必须作为合法中间状态。若把 Bill.total_amount 与 paid_amount 当作唯一真相，账单项目的来源和付款历史都难以核对；若把每次缴费覆盖在账单行上，则无法解释多次支付或失败付款。

Meter 保存设备和其房产归属，MeterReading 保存一系列随时间增加的读数。历史读数不能被最新值覆盖，否则费用计算无法回溯。查询需求包括某房当前有效表计、指定时间段读数、账期应收和实收，以及年度各月收缴率。金额统计既要排除失败付款，又要保留没有付款的账单，因此报表口径从需求阶段就必须明确。

### 2.2.3 租赁、停车、通知与文件的各自事实

申请中介协助出租的授权、公开挂牌、最终租赁合同是不同的业务事实；不能把一条授权记录直接当作已签约合同。停车业务也要区分车辆、申请和许可，不能用停车位表是否存在来替代车证审批。通知属于一次发送事件，而 recipient_role、delivery_status、read_at 属于通知与具体接收人之间的关系；同一通知对不同人可以分别已读或未读。户型图文件的对象内容在 MinIO，房产或模板与对象的关联在 MySQL，二者要能够按对象键对账。

这些子域在最终快照中的数据完备程度不同。例如通知有 7 条、收件关系有 507 条，车证有少量车辆、申请与许可；但正式合同、实际车位占用和空间边界表最终为空。需求分析呈现系统打算表达的事实类型，后面的验证章节再明确哪些被当前演示数据覆盖，避免把“设计了表”当成“完成了全部场景”。

## 2.3 写入事务与查询需求

### 2.3.1 需保持一致的状态变更

入住办理至少牵涉人员资格、房产当前占用状态、Residence 新记录和 PropertyUnit 状态或版本。若 Residence 插入成功而房产状态更新失败，后续页面会对“是否有人入住”给出相互矛盾的答案。服务层因此需要把属于同一办理动作的数据库写入置于事务中，并用条件更新或版本字段处理同时办理的竞争。账单出账也要防止同房同月重复，通知发送则应确保通知主记录与具体收件关系按可解释的边界写入。

一致性不是抽象口号，而可变成负向输入：账单指向不存在的房产应由外键拒绝；同一账期重复出账应由业务唯一键拒绝；同一表计同一时刻重复读数应被唯一键拒绝；不合法金额、日期和状态组合由 CHECK 或业务校验拒绝。历史上 2026-08-30 的入住失败日志提供了更强的运行例子：某项 CHECK 冲突导致多步骤办理中的写入回滚。必须同时说明，之前独立完成的“创建人员”HTTP 请求并不属于这次入住事务，不能夸大为整条跨请求流程都原子化。

### 2.3.2 分页、统计和下钻

528 套房虽不大到必须采用分布式系统，但足以让“全部行一次性返回、前端自行筛选”变得不合理。房产、住户、账单等列表需要统一的筛选条件、COUNT 总量与 LIMIT/OFFSET 当前页；不同角色的 COUNT 和页面行必须应用相同的数据范围，否则会发生“显示 528 条、实际只有 72 条可翻”的错误。年度统计从真实账期出发，月度再下钻到小区及明细；不存在账单的月份应表现为无数据，而不是伪装为零元出账。

统计还要求口径可解释。月度收缴率分子是该账期 SUCCESS 付款形成的实收，分母是账单项目汇总的应收；分母为零时不能直接除。收费类型构成、欠费排行和占用率各有不同的底表及过滤条件，不应把 Dashboard 误解成一条万能 SQL。答辩时的可追踪性需求是：能从页面指标沿 API、Controller、Service、Mapper XML 查到参与计算的表或 View，并说明 JOIN 与 WHERE 的业务意义。

## 2.4 非功能要求与规模口径

### 2.4.1 一致性、隔离、性能与恢复

完整性优先于界面“看起来正确”。核心外键和唯一键不能依赖前端验证；权限隔离不能依赖页面隐藏；性能优化需针对真实过滤、JOIN 和排序列，并用执行计划比对，而非仅凭增加索引个数判断。备份恢复应验证中文字符、View、约束、历史版本以及 MinIO 对象，而不能以容器显示 Running 作为数据仍在的证明。

项目最终规模属于课程设计级结构化演示数据。它有足够的关联行来观察索引、聚合和数据范围变化，但负载测试只说明特定机器、场景和时间窗的结果；不能外推为生产吞吐保证。Redis 自动检测及故障降级是可用性设计的一部分，尚无证据表明它为某条具体业务查询带来了可量化的缓存加速。高德地图使用普通经纬度记录和外部服务接口，也不是 MySQL POINT 或空间索引实验。

# 第三章 数据库概念结构设计

## 3.1 建模方法与全局概念图

### 3.1.1 全局图只回答“有什么业务对象、怎样相关”

概念设计从现实中抽取稳定对象及业务关系，而不是先照着页面按钮建表。全局概念图把小区、楼栋、单元、房产组成空间主线；Person、Ownership、Residence 构成人房主线；FeeType、FeeStandard、Bill、BillItem、Payment 构成收费主线。它只回答“有哪些核心对象、它们有什么关系”，不展示字段、主外键、Mapper 或运行组件。这样做可以让非开发读者先讨论关系是否真实，再进入实现细节。图中 PropertyUnit 是汇合点，因为绝大多数业务事实最终都能定位到具体房屋。

概念图不应把所有关联画成一条没有语义的“关联”线。例如 Person 与 PropertyUnit 可以分别为拥有、居住和租赁授权，三者虽然端点相同，发生条件、时间属性、删除规则及查询含义却不同。将其明确区分，才能在逻辑模型中得到 Ownership、Residence、Authorization 等不同关系表。同理，Notification 与 Person 的多对多并非仅是发送名单；已读时间和投递状态必须附着在每一个接收关系上。

**图 3-1 位置：**全局概念 ER 图。图注：“核心实体和业务联系，不表示字段、主键、外键或数据库表的完整清单。”需避免将发送范围筛选框画成持久化实体。

## 3.2 空间资产子域

### 3.2.1 Community→Building→BuildingUnit→PropertyUnit

一个小区可包含多栋楼，一栋楼含多个单元，一个单元含多套房；父子方向决定外键应置于子记录。这样可以在房产行上仅保存 building_unit_id，经单元、楼栋反查社区。若把完整地址各层复制到每套房，房产数越多，更名和纠错越容易产生修改异常；将楼栋和单元作为独立对象，使“楼栋规模”“某社区有哪些楼栋”也可以直接查询。

空间层级同时承担权限归属路径。管理员查看某房时，Service 可沿 PropertyUnit→BuildingUnit→Building→Community 确定其真正所属社区，不能仅依据请求参数声称该房在自己有权管理的小区。统计查询从房产汇总到小区时亦沿这一结构 JOIN；因此它既是业务组织结构，也是数据范围控制的基石。全局图应清晰呈现这些 1:N 关系，却不应让小区直接重复连接每张账单，从而制造多余的概念联系。

### 3.2.2 户型模板与物理房产不是同一对象

户型模板描述可重复使用的布局设计，PropertyUnit 是现实中独立存在的一套房。若把默认户型图复制到每套同户型房产，不仅浪费对象存储，还使模板更新需要多处同步。项目后续演进中引入模板默认图和面积变体图：先依据房屋的模板与面积选择共享资源；需要房产专属图时才由单房关联覆盖。这是“共享描述”与“实例事实”分离的典型例子。

最终快照存在默认模板和面积变体的关系记录，并有对象存储样本，但房产专属关联为零。因而本报告讨论设计的选择顺序和真实预览链，不宣称已经对每套房手工制作单独户型图。文件的业务索引在 MySQL，二进制在 MinIO，概念图只表示“房产采用模板”“模板关联图”，不把 Bucket 当作物业实体。

## 3.3 人员、产权与居住子域

### 3.3.1 Ownership 与 Residence 的关系属性

假设甲拥有 A 房却住在 B 房，乙租住 A 房。如果 PropertyUnit 仅设置 owner_person_id 和 resident_person_id，短期看似可用；但当 A 房出售或乙搬离时，覆盖这两个字段会抹去旧关系，无法回答“上月谁住在这里”“这笔历史账单归属何种关系”。如果一个人可以与多套房有关系，单外键又无法表达完整的基数。项目因此把人房之间的关系实体化：Ownership 表达产权，Residence 表达居住，各自有开始和结束时间以及业务身份属性。

关系表不仅解决 N:M 的数量问题，更解决关系属性应放在哪里的问题。产权份额属于某个人对某套房的产权，而不是 Person 的永久属性，也不是 PropertyUnit 的通用面积属性；居住的角色和预期结束时间同样属于某次入住。把这些信息放在联系实体上，才能让一个人的不同房屋关系互不覆盖，也让一套房的历次人员变化形成可查询的历史。

### 3.3.2 当前关系与历史关系

当前状态可以由结束时间为空或生成的“当前键”识别，历史记录仍保留。MySQL 对普通 UNIQUE 中的 NULL 允许多行，这对历史记录有用，却不足以单独表达“同一对象只能有一个当前有效关系”。最终 Schema 中通过生成列和唯一键约束部分当前态，例如当前居住与当前责任住户。它们把“仅当前记录受唯一性限制”转为数据库可执行条件，而不是靠页面禁用按钮。

产权必须按最终 DDL 准确描述。V3 曾要求当前一房一名业主且份额为 1；最终 2026-09-01 备份中，产权份额 CHECK 放宽为大于 0 且不超过 1，唯一键为 person_id 与 current_property_unit_id 的组合。这防止同一个人对同一套房存在两条当前产权记录，但并不禁止不同人分别对同一房拥有当前产权。最终库也未见“多人份额合计必为 1”的跨行约束。历史迁移与最终状态的差异，是第八章讨论迁移链来源缺口的重要例子。

## 3.4 收费与计量子域

### 3.4.1 FeeType、FeeStandard、Bill、BillItem、Payment

“物业费”首先是一类费用，而不是某月某房的一笔应收。FeeType 给出费用类型身份，FeeStandard 给出社区和生效期内的定价规则；生成账单后，BillItem 保存本次出账采用的数量和单价快照。即便将来标准发生变化，旧账单仍按当时确定的项目计算，不应通过当前 FeeStandard 值回算历史金额。Bill 将多项目归于同一房产与账期；Payment 则单独记录实际资金事件及成功状态。

这种拆分使 SQL 更长，但事实边界更清楚。若把费用类型、数量、标准单价、账期和已付金额塞进一张“收费表”，一张账单多项目就需重复房屋及账期信息，部分付款又难以分辨是一次还是多次资金动作。当前模型允许一张 Bill 对应多条 BillItem，也允许多条 Payment；财务汇总再按 bill_id 聚合。必须同时承认其边界：付款与账单关联，未提供可证实的“每笔付款分摊到每个费用项目”关系，因此无法从总欠费准确推出某个 FeeType 还欠多少。

### 3.4.2 Meter 与 MeterReading 的设备—历史分离

表计的编号、类别、启用状态相对稳定，读数则按采集时间不断追加。两者分离后，查看最新读数只需从历史中按时间选取，费用核对也可回到特定账期的读数。对同一 meter_id、reading_at 设置唯一规则，可以阻止同一时刻重复插入；对读数取值设置非负等规则，可减少明显不可能的输入。这些约束不能取代异常读数检测，却能守住基本结构边界。

最终快照的 1584 个表计与 15840 条读数呈精确的每表计十条关系；这说明数据生成具有明确规则。报告使用它们展示一对多历史查询和索引效果，不声称表计读数来自真实长期硬件采集。Stage H 的模拟器曾以 INSERT IGNORE 和唯一键实现幂等插入验证，其意义在于说明重复采集如何被数据库键阻断，而不是证明完整物联网采集系统已经建成。

## 3.5 其他需要实体化的业务联系

### 3.5.1 授权、挂牌和合同的不同阶段

房产所有者请求中介协助出租时，授权记录说明谁准许谁在何种房产与时间范围内办事；挂牌记录说明房屋已经进入可展示的出租状态；合同则代表更晚的签约事实。把三者揉成一个 listing.status 字段，会让“尚在寻找中介”“已挂牌但未租出”“已签合同”共享一行且难以保留阶段证据。项目使用独立表及关系约束表达这些阶段，部分复合外键进一步要求授权与挂牌所指房产一致，阻止“引用了存在的授权，但授权属于另一套房”的逻辑错误。

最终备份有 80 条挂牌和 64 条授权，但 lease_contract 与 contract_participation 为空。因此当前可以解释挂牌和授权模型、查询与部分页面，不能把空合同表写成签约业务已用最终数据完成验收。这一对比反而说明概念模型可以比本轮演示业务覆盖更广，但报告必须分别标识“结构支持”和“实测闭环”。

### 3.5.2 车证与通知中的“关系也有自己的状态”

车证的申请和正式许可不能合并：申请可能待审、拒绝或通过，许可只有审核后才具有明确有效期和车辆关联。Notification 与 Person 之间同样不是一条简单关联线。一条通知可发给多人，同一个人也会收到多条通知；每人的 TO/CC、送达和已读情况不同，所以 NotificationRecipient 是具有自己属性的联系实体。发送时按小区、楼栋或房产筛选目标，只是服务层将范围解析为具体 Person 的过程，不能画成 Notification 对这些范围的直接持久化外键。

# 第四章 数据库逻辑结构设计与范式分析

## 4.1 ER 到关系模式的转换

### 4.1.1 层级外键与时态联系表

空间层级中的每个 1:N 联系均由 N 端保存其父对象的外键：Building 属于一个 Community，BuildingUnit 属于一个 Building，PropertyUnit 属于一个 BuildingUnit。实体的技术主键提供稳定引用，社区编码、楼栋编号、房号等自然标识再由相应业务唯一约束控制。这种“主键用于关系稳定、业务键用于业务识别”的双层设计，避免了名称变化需要级联修改外键，也避免了技术 ID 不能阻止重复房号的问题。它还让后续收费与作用域查询可以用相同的层级 JOIN 追溯归属社区。

Person 与 PropertyUnit 的产权、居住属于具有时间属性的多对多联系，转换为 Ownership、Residence 两张独立关系表，各自保存两端外键与关系自身属性。若仅在 Person 里存 property_ids 字符串，不仅违反列值原子性，还无法对每段关系分别设置日期、角色和参照完整性；若仅在 PropertyUnit 存 current_person_id，则历史覆盖后无法还原。联系表并不意味着允许所有任意组合，仍需用日期约束、当前态唯一键以及服务事务定义合法状态。

### 4.1.2 弱实体、三元授权与收件关系

BillItem 的存在依赖 Bill。项目编号在某张账单内部才有意义，账单项目的唯一识别应连同 bill_id 考虑；即使实现采用独立技术 ID，也需要约束同一账单下的项目序号或费用类型组合的业务意义。项目的数量、单价和金额都属于当次账单快照，不应放回 FeeType 的全局定义行。NotificationRecipient 也是联系实体：通知主记录只说明“发送了什么”，接收行说明“谁收到、以什么角色、何时读”。这类联系上的属性没有合适的归属端，故不能省略中间表。

租赁授权涉及 Person、PropertyUnit 和 Agency 等多个业务对象。一条授权只校验 authorization_id 存在仍然不够，因为后续挂牌可能把另一套房与这条授权配对；复合外键使“引用存在”进一步提升为“引用的是同一业务组合”。从概念图转为逻辑模型的关键，并非机械地把每个菱形变成一张表，而是看联系是否具有独立属性、历史与一致性规则。对于收费、通知和权限，答案均是肯定的。

## 4.2 候选键与函数依赖的代表性推导

### 4.2.1 空间层级与产权/居住的依赖

设 property_unit_id 是房产主键，则有 property_unit_id → building_unit_id；单元键决定 building_id，楼栋键又决定 community_id。于是 property_unit_id 经由外键链可以确定 community_id。若在 property_unit 中反复存 community_name，就形成通过非主键层级对象导出的传递依赖：楼栋移到另一社区或社区更名时，多套房的复制值可能不一致。当前逐级外键消除了这一类更新异常。需要直接按社区筛选时，SQL 使用层级 JOIN 或经验证的冗余索引路径，而不是放弃关系来源的一致性。

对于产权与居住，一条记录的技术主键可唯一标识它，业务上“某人—某房—某次开始时间”也近似一段关系的候选标识，但必须谨慎：仅凭这三个字段不总能涵盖补录、同日起止或角色变更规则。数据库中的实际 UNIQUE、生成列与日期 CHECK 才是本项目实施的约束，函数依赖推导只是说明为什么 Person 的姓名、PropertyUnit 的地址不应复制到每条关系行。查询展示这些信息时 JOIN 原表，关系表只保存这段关系自身的性质。

当前与历史还有另一层依赖：一条历史居住记录可以有结束时间，同一房可以累积多条历史；“房产→当前责任住户”是一条条件函数依赖，而非全历史范围内的函数依赖。将当前房产键在满足状态条件时生成、历史时设为 NULL，再施加 UNIQUE，能把这一条件规则放进物理 Schema。普通的 UNIQUE(property_unit_id,end_at) 不能自然完成同样效果，因为多条 end_at=NULL 的当前行并不彼此冲突。

### 4.2.2 账单与账单项的局部依赖

Bill 的候选业务键是同一 property_unit_id、billing_year、billing_month 的组合；一个房产的一个账期不应有两张相同账单。BillItem 则在 Bill 内部按项目区分，可以表示为 (bill_id,item_no) → fee_standard_id、quantity、unit_price、amount 等当次快照。item_no 单独不能决定这些字段，因为每张账单都可能有“第 1 项”；bill_id 单独也不能决定它们，因为一张账单有多个费用项目。让非键属性依赖整个组合键，而不是其中一部分，是账单项目满足第二范式的关键。

FeeStandard 记录社区、费用类型、生效日期对应的定价规则，BillItem 仍保存实际采用的 unit_price。这并不是单纯错误的重复：出账时确定单价，此后标准可能变更或停用，历史账单应保持“当时出账依据”。应当把快照的取值时点和不可随意重算视为业务规则，而不是把每次查询都 JOIN 最新标准。如果保存的快照金额与生成规则有冲突，再通过 generated STORED amount=ROUND(quantity×unit_price,2) 把一部分冗余风险转为数据库计算规则。

Payment 与 Bill 的关系进一步说明为何不能把 paid_amount 存在 Bill 作为唯一资金事实。Bill 的账期和出账事实决定应收项目集合，付款却可多次发生且有 SUCCESS、失败等状态。若 Bill.paid_amount 被手工累加，重试、撤销或异步回调可能使它与资金记录不同步。通过独立 Payment 行再聚合成功金额，统计能够回到原始交易事件核对；其代价是财务视图与报表 SQL 更复杂。

### 4.2.3 账号与社区范围的复合键

account_community_scope 使用 (account_id,community_id) 作为复合主键：一个账号与一个社区的授权关系至多出现一条，而同一账号可以有多个不同社区行。status、assigned_at、assigned_by_account_id 描述这一次授权关系，不属于账号总体，也不属于社区总体。以该复合键为决定因素时，非键属性依赖完整的账号—社区组合，而非某一半。把社区 ID 列表放进 app_account 的 JSON 或逗号字符串，会让数据库无法使用普通外键逐一保证每个社区存在，也难以对授权状态与时间单独审计。

这一结构直接服务课堂上“一个管理员管多个小区”的疑问：多小区不是给 account 加第二个 community_id 列，也不是为每个小区创建重复账号，而是多条作用域关系。服务读取有效授权后形成 communityIds，查询时传给 Mapper。关系结构、功能权限和 SQL 过滤由此形成连续链条，第六章将使用一个单社区员工与双社区员工的历史验收值核对其效果。

## 4.3 1NF、2NF、3NF 与工程折中

### 4.3.1 原子性与复合键完整依赖

第一范式强调关系中的列值应保持可作为单个业务值处理的原子性。空间层级各有独立键，账号授权每社区一行，账单每费用项目一行，收件关系每接收人一行，均避免了把多个实体 ID 拼进一个业务列。这样做让数据库可以建立外键与索引，让 SQL 可以只筛选目标关系，也让一条关系的变化不迫使读取、解析和重写整段字符串。

第二范式针对具有复合候选键的表：BillItem 的项目数据依赖 bill_id 与项目标识的整体，account_community_scope 的授权状态依赖账号与社区组合，而不是只依赖账号或只依赖社区。第三范式进一步要求非键属性不要经由另一非键属性传递决定。例如房产行经单元→楼栋已能确定社区，不应另复制社区名称作为权威事实；账单行经房产可以找到小区，账单不应自造一条不受约束的社区名称。这里的“满足范式”是对选定事实归属的分析，不是对几十张表一概而论的证明。

| 关系 | 主要决定关系 | 若错误合并 | 采用的分解与收益 |
|---|---|---|---|
| PropertyUnit | property_unit_id → building_unit_id → building_id → community_id | 逐房复制社区名，改名时出现修改异常 | 各层独立，逐级 FK；社区归属可追溯 |
| Bill 与 BillItem | (bill_id,item_no) → 项目快照 | 一张账单多项目重复账期和房号 | Bill 管账期，BillItem 管项目 |
| Bill 与 Payment | payment_id → 付款金额与状态 | 一个 paid_amount 覆盖多次付款历史 | 付款逐条保存，成功额聚合 |
| account_community_scope | (account_id,community_id) → 授权状态与时间 | 账号存社区列表，无法逐项 FK 与审计 | N:M 关系实体化，逐行授权 |
| NotificationRecipient | (notification_id,person_id) 及业务接收维度决定状态 | 通知主表只能存一个 read_at | 每个接收关系独立送达、已读 |

### 4.3.2 快照、生成值和 JSON 的审慎表述

正规化并不禁止一切冗余。BillItem 的 unit_price 是历史定价快照，若只保存 fee_standard_id 而在展示时永远取现行标准，就会改变旧账单语义；amount 则由数据库生成，避免应用重复计算造成的舍入差异。当前态生成列不是新的业务事实，而是将“仅活动行参与唯一性”这一条件规则转换为数据库索引可以处理的值。它们是受控冗余或物理约束实现，设计报告应写清来源和同步机制，而不是简单称为“完全 3NF”。

notification_recipient.payload_json 保存针对接收人的扩展载荷。JSON 在此用作随通知类型变化的附属内容，并不替代 Person、Notification 和两者之间的主关系键。其优势是减少为每种通知新增列的迁移；代价是库内不能轻易对每个载荷属性建立普通外键和统一 CHECK。因此涉及可靠筛选、统计或权限的身份与状态仍由关系列承担，JSON 不应变成未建模业务关系的仓库。V5 对这一列的扩展反映了需求演化，而非对 1NF 的无条件放弃。

# 第五章 数据库完整性、约束、索引、视图与物理设计

## 5.1 实体、参照与用户定义完整性

### 5.1.1 主键与业务唯一键

技术主键保证每行可以稳定引用，却不会自动阻止业务重复。例如 Bill 的 bill_id 不同，仍可能代表同一房产同一账期的两张账单；因此需要 (property_unit_id,billing_year,billing_month) 的业务唯一约束。同理，MeterReading 即使每行有自己的 ID，也应阻止相同 meter_id 与 reading_at 的重复读数。账号授权采用 (account_id,community_id) 的复合键，防止同一账号对同一社区出现两条相互矛盾的授权状态。

业务唯一键是从现实规则推导的。制定约束前须明确“什么算同一个”：房号通常只在单元或楼栋内部唯一，不能全库仅凭“101”判重；费用标准的生效日期也要与社区和费用类型共同理解。对账单项目，项目序号离开 bill_id 没有身份。数据库层约束比页面“提交按钮禁用”更可靠，因为 API 重试、脚本导入和并发请求都可以绕过前端。历史 NEG 负例通过故意制造重复标识，证明键不是仅写在设计文档里。

| 业务事实 | 关键唯一维度 | 若缺失的异常 | 验证来源 |
|---|---|---|---|
| 房产的单元内识别 | 所属空间层级与房号/编码 | 同位置出现两套同号房 | V1 DDL、NEG-01～03 的层级重复输入 |
| 某房某账期账单 | property_unit_id、billing_year、billing_month | 重复出账并重复计入应收 | V1 DDL、账单查询 |
| 同一时刻的表计读数 | meter_id、reading_at | 幂等采集变成重复历史 | MeterReading DDL、模拟器插入链 |
| 账号社区授权 | account_id、community_id | 同一授权范围出现冲突状态 | V4 DDL、权限查询 |
| 当前有效关系 | 生成的“当前键”及业务组合 | 同时出现冲突的当前入住/挂牌等 | 最终备份 DDL |

### 5.1.2 外键、复合外键与删除策略

参照完整性的第一层是“被引用对象必须存在”：房产不能指向不存在的单元，账单不能指向不存在的房产，账单项目不能成为没有账单的孤儿。V1 负向测试中，缺失空间父对象和孤儿账单项目的输入被拒绝。这类约束直接防止页面查询中出现“账单有记录、房屋详情为空”的数据裂缝。对历史业务，随意级联删除父记录往往比限制删除更危险；一套房的历史账单、付款和居住关系不应因为房屋被停用而消失。最终删除策略应以 DDL 中每条 FK 的 ON DELETE 行为为准，不能泛称所有关系都 CASCADE 或都 RESTRICT。

复合外键表达比“引用 ID 存在”更强的组合规则。假设挂牌 L 引用授权 A 和房产 P；如果 A 实际授权房产 Q，两个单列 FK 都满足，却产生错误配对。复合 FK 把授权标识与房产标识作为同一参照组合，数据库便能拒绝该输入。V1 的 NEG-15 专门覆盖了“授权存在但房产不匹配”的情形，说明参照完整性不仅是防止孤儿行，也能保护业务语义一致。

一些跨服务关系无法仅靠单个 FK 完成。例如 MinIO bucket/key 存在 MySQL 中，数据库 FK 不能证明对象存储内一定有这个文件；这需要部署恢复时额外对账。多态的空间边界 subject_type+subject_id 也不能自然成为同时指向 community/building 的普通外键。完整性设计因此有分层：数据库能约束的键必须落库，跨存储或跨类型的规则则要通过服务检查、批量核验和明确的异常处理补充。

### 5.1.3 CHECK、状态组合和时间边界

CHECK 适合表达行内可判定的不变量，如份额范围、数量及金额边界、日期先后顺序和某些状态组合。V1 的负向 SQL 用不合法的产权/居住日期、授权组合、设施移动性等输入验证约束。它们与 Service 校验并不冲突：Service 给用户清楚的错误信息，数据库 CHECK 则防止其他写入通道绕过服务时破坏最终事实。2026-08-30 运行日志里出现的 CHECK 3819 也说明它会在真实多步骤流程中产生影响，必须配合事务回滚处理，而不是把 SQL 异常直接吞掉。

CHECK 的能力边界同样清楚：它通常评估当前行，不能直接汇总“同房所有产权人的份额之和等于 1”，也不能证明网络另一端 MinIO 对象存在。跨多行或跨存储的规则需要事务内查询、锁或后续一致性扫描。对于状态字段，单纯允许若干枚举值还不够，还要思考某一状态是否需要额外时间字段、是否能从旧状态合法流转。项目现存表中有结构预留和阶段差异，不把所有状态机都写成已完全验证的能力。

## 5.2 当前态与历史态的物理约束

### 5.2.1 最终 Schema 中的生成列唯一

历史关系表必须允许同一房产曾多次出租、入住或授权，而当前有效状态往往要求唯一。如果直接 UNIQUE(property_unit_id,end_at)，MySQL 允许多条 end_at 为 NULL 的行，无法防止两条“未结束”记录。最终 Schema 中的某些关系通过生成列在有效行上输出 property_unit_id 或 person_id，在无效/历史行上输出 NULL，再对生成列建唯一键。这让有效行相互冲突、历史行保留，体现了“条件唯一”规则的物理实现。

例如当前责任住户唯一与普通当前居住关联应区分：一套房可能允许多人共同居住，但责任住户按业务只能有一个；前者不能被误写成“一房只能有一个在住 Person”。当前挂牌也要限制一套房同时重复公开挂牌，而历史挂牌仍可保留。应用层的入住、搬出和挂牌更新通过事务维护状态，数据库生成唯一键为并发竞争提供最后防线。表中各生成列准确名称与条件应按附录的最终 CREATE TABLE 核对，正文重点讨论约束原理与所保护的业务事实。

### 5.2.2 产权规则必须以最终备份为准

产权是迁移演进中最需要避免“看旧文件讲现状”的例子。V3 的规则包含“一房至多一位当前业主”和当前份额为 1 的限制，而最终 2026-09-01 备份允许 share 大于 0 且不超过 1，并以 person_id 和 current_property_unit_id 的组合唯一。后一规则允许不同人员各自对同一房产有当前产权；它只阻止同一人同一房重复当前记录，不能自动保证所有份额加总为 1。若报告仅引用 V3，就会把最终数据库讲错；若仅看最终 DDL，又会漏掉系统曾经改变产权表达能力的开发事实。

这项差异的原始 ALTER 迁移尚未在 V1—V10 中定位，不能编一个“Vx 将份额从 1 改为区间”的具体版本。可证实的是两份结构材料各自的规则，以及它们之间存在差异。对于共享产权真正需要的“份额总和”约束，单行 CHECK 不够，未来若要上线该能力，应定义事务边界或聚合校验及并发策略。这既是逻辑模型分析的边界，也是迁移纪律的反思素材。

## 5.3 查询模式驱动的索引设计

### 5.3.1 多社区范围与层级 JOIN

索引应从高频谓词出发，而不是给每列机械加索引。多小区工作人员查询房产时，SQL 常由 community_id 限定范围，再沿 building、building_unit、property_unit 联接，并按业务筛选条件分页；因此父子外键列与社区范围列需要适当访问路径。账单列表的账期、状态和房产归属也要求过滤列与排序列配合。联合索引的列顺序直接影响能否利用左前缀：若查询先按账期定位大量房产，再按状态筛选，房产领先的唯一键不一定帮助跨房产账期报表。

最终快照的索引规模需要按“索引对象”和“索引列明细行”区分。历史审计中，20 张核心表统计到 69 个索引对象，而 information_schema.statistics 的 208 行是联合索引逐列展开后的记录，并不是 208 个独立索引。课程报告更应解释具体索引服务了哪类查询、是否带来写入成本，而不是用一个大数字表现复杂度。

### 5.3.2 账期状态联合索引的前后对比

V1 已有 uk_bill_property_period(property_unit_id,billing_year,billing_month)，它很好地阻止同房同账期重复出账，也适合从某房查历史账单。但统计页常查询“给定年份、月份和状态下，所有房产的账单”。由于领先列 property_unit_id 在这种查询中未给出固定值，该唯一键无法自然替代账期优先的访问路径。V6 为此增加 idx_bill_period_status(billing_year,billing_month,status,bill_id)，使数据库先按账期缩小集合，再按状态继续筛选，bill_id 也可辅助随后定位行或关联。

Stage G 的代表性 EXPLAIN ANALYZE 对比记录显示，选定查询的检查行数约由 603 降为 11，执行时间约由 0.85 毫秒降为 0.13 毫秒。这个结果能够支持“该查询样本在当时的数据和执行环境下受益于新索引”，不能扩大成所有统计均提速相同比例；数据量、缓存状态、参数分布和优化器选择变化都会影响绝对数值。更重要的教学结论是：唯一键与查询索引解决不同问题，二者不是互斥的重复建设。

| 对照项 | V6 前可用主要键 | V6 新增键 | 代表性历史记录 |
|---|---|---|---|
| 目标查询 | 跨房产按账期、状态筛选 | 同左 | Stage G SQL 性能审计 |
| 索引列序 | property_unit_id、year、month | year、month、status、bill_id | 过滤前缀更贴近 WHERE |
| 检查行数 | 约 603 | 约 11 | 仅为该次 EXPLAIN 样本 |
| 执行耗时 | 约 0.85 ms | 约 0.13 ms | 不等于全系统吞吐提升 |

### 5.3.3 分页、排序与未完成优化

房产列表用 COUNT 获取符合条件的总量，再用 LIMIT/OFFSET 读取一页，并只允许约定的排序字段。这样比一次返回 528 行更适合未来数据继续增加，也让当前页的行数与总记录数有各自清晰的来源。不过 OFFSET 很深时，数据库仍可能扫描并跳过大量前置行；第 1000 页的代价不等于第一页。若未来数据显著扩大，可按稳定排序键研究 keyset pagination，但本项目没有该方案的最终实现证据，不能提前写成现有成果。

索引也有代价：每插入新账单或读数需要维护相关索引，联合键过多会增加存储和写入工作。项目当前索引设计依托真实列表、账期统计与外键关联；对已有演示规模，应优先通过 EXPLAIN 证实瓶颈，再决定是否继续添加。安全排序在 XML 中通过预设字段白名单或 choose 分支控制，用户输入的列名不能像数值参数一样无条件进入 ORDER BY 文本。

## 5.4 财务 View 与聚合口径

### 5.4.1 单账单应收、实收与欠费

一张账单可有多条 BillItem，也可有多条 Payment。如果直接 Bill LEFT JOIN BillItem LEFT JOIN Payment 再 SUM，假设一账单有 3 项、2 笔付款，就会得到 3×2=6 行中间结果，导致应收和实收都重复计数。最终 v_bill_financial_summary 避开这个乘法效应：首先按 bill_id 对 BillItem 单独 SUM(amount) 得应收，再按 bill_id 对 status='SUCCESS' 的 Payment 单独 SUM(amount) 得实收，最后把两组一账单一行的结果分别 LEFT JOIN 到 Bill 主集合。Bill 是主集合这一选择具有业务意义：即使一张账单暂时没有付款，它仍然是待收账单，不应从报表消失。

INNER JOIN 会丢弃没有 SUCCESS Payment 的账单，使欠费被低估；RIGHT JOIN Payment 更会把“已发生付款”错误当成账单全集。LEFT JOIN 后的空聚合值用 COALESCE(...,0) 转为“该账单已存在，但当前成功付款合计为 0”，与“这个月根本没有账单”完全不同。应收与实收各自 ROUND 到两位小数，欠费使用 GREATEST(应收－实收,0) 防止超额付款出现负欠费。该截断提供报表口径，不意味着超额付款业务已被完整解决；超收处理仍应在业务规则中单独定义。

下表是**公式演示计算，不是最终备份中某一特定 bill_id 的实际值**。它使读者可手算校验 View 的逻辑；正式提交时若需替换为真实账单行，应从同一快照同时取出 Bill、BillItem 和 SUCCESS Payment，不能混用不同时间点的数值。

| 场景 | BillItem 项目金额 | SUCCESS Payment | 失败 Payment | View 应收 | View 实收 | View 欠费 |
|---|---|---|---|---:|---:|---:|
| 部分缴费的演示账单 A | 物业 100.00＋水费 50.00 | 60.00 | 20.00 | 150.00 | 60.00 | 90.00 |
| 尚未缴费的演示账单 B | 物业 100.00＋电费 40.00 | 无 | 无 | 140.00 | 0.00 | 140.00 |
| 完全缴清的演示账单 C | 物业 100.00＋水费 50.00 | 100.00＋50.00 | 无 | 150.00 | 150.00 | 0.00 |

账单 A 中失败付款 20 元不计入实收；账单 B 尽管没有 Payment 聚合行，仍由于 Bill 主表和 LEFT JOIN 保留在 View 中；账单 C 的两次成功付款聚合后恰好抵消应收。数据库备份中的 View 定义位于最终视图结构部分，不能把导出文件前面为导出顺序生成的临时“1 AS ...”占位结构误认作实际 View SQL。该 View 只计算账单级欠费，没有付款分配到 BillItem 的记录，所以不能把 90 元说成“水费欠 90 元”。

### 5.4.2 月度 View 与统计页面

v_monthly_collection_summary 在单账单应收、实收和欠费口径之上按 billing_year、billing_month 分组，计算 bill_count、三项金额合计与 collection_rate。收缴率的分子是成功实收之和，分母是应收之和，比例再乘 100；NULLIF(SUM(receivable),0) 使应收为零时分母变为 NULL，避免除零错误。NULL 的意义是“这一比率在该分母下不可定义”，不能机械显示成 0% 并误导读者为“已出账但一分钱未收”。

管理端统计还必须应用用户社区范围，不能直接把全库的月度 View 总数原样返回给仅管一个小区的员工。因此部分 StatisticsMapper 查询从 v_bill_financial_summary 出发，再经房产层级 JOIN 社区并作范围过滤、重新分组。Dashboard 某月收费图、月报、年度报表都基于真实账期数据；年度页面为显示完整 1—12 月横轴，在前端补齐缺失月份的维度，但把没有账单的业务指标保持为 null，不制造 0 元账单。这个展示规则避免了“未来月份尚未出账”与“本月存在账单但金额为零”的混淆。

| 某年 8 月无账单 | 否 | 8 月 | null，不绘柱和折线点 | 暂无账单数据 |

## 5.5 类型、编码与物理存储边界

### 5.5.1 字段类型与跨存储位置

金额用定点数和明确舍入规则表达，不能让前端浮点运算成为最终账务事实；账期年份、月份应分别有合法范围，时间字段保存事件发生及关系有效期。状态列使历史记录可保留，CHECK 与 UNIQUE 将常见非法组合挡在数据库边界。空间位置以经纬度和相关 JSON/业务列保存，结合高德 Web Service 和前端地图展示；项目未实现可证实的 MySQL POINT/SPATIAL INDEX，因此不把地图功能归为数据库原生 GIS 检索。

MySQL 的 file_object 保存 bucket、object_key、content_type、hash 等可查询元数据，MinIO 保存图像字节。分层有利于以外键组织文件用途，也防止二进制文件干扰常规业务表扫描，但两套存储必须额外核查对象存在性和清理孤儿对象。最终恢复过程中核对了关系元数据与对象键样本，这比仅看到网页可以显示图片更能证明存储链。编码方面，Docker 恢复曾验证中文数据和字符集，说明跨 Windows 导出、容器内恢复时需要关注字节安全；具体恢复方法将在第八章展开。

# 第六章 多小区权限与数据范围控制

## 6.1 账号与社区的多对多授权模型

### 6.1.1 Role、Permission 与 Scope 的职责

“有房产管理功能”与“能管理全部房产”是两个完全不同的命题。Role 与 Permission 定义允许调用的功能类型，例如查看房产、维护费用或发送通知；account_community_scope 定义一个账号实际被分配了哪些社区。前者控制接口入口，后者控制结果集和具体对象。若只做角色，所有 PROPERTY_STAFF 可能看到全部社区；若只做作用域而不做角色，任何被关联到一个社区的普通账号也可能调用管理员操作。系统通过这两层共同回答完整的访问问题。

Account 与 Community 在授权层是 N:M。account_community_scope 的一行代表某账号对某小区的一次授权关系，复合主键阻止同一组合出现冲突副本，status 可以表示是否有效，assigned_at 和 assigned_by_account_id 保留授权来源。这比在账号表中设置 community_id 一列有更好的表达力：一个人负责两个小区只需两行，不需“community_id_2”；撤销其中一个小区的范围也不影响另一个。它更优于逗号拼接字符串，因为数据库可分别检查每个社区存在并可按社区查负责人。

系统管理员的全局权限与普通员工的 scope 行不能混成同一种语义。具有 SYSTEM_ADMIN 身份时，可按特定全局分支访问管理域；PROPERTY_STAFF 则必须从有效范围行得到社区集合。权限分支由服务端身份与角色决定，不能让前端通过传递 global=true 之类参数抬升权限。最终是否可以写某个对象，还需检查对象本身是否落入有效范围，而不能仅因为员工能看到某个管理页面就放行。

### 6.1.2 作用域的有效与空集合

DataScopeService 从已认证账号及 account_community_scope 读取当前有效 communityIds。集合为空时，对非全局角色应当“拒绝任何社区行”，而不是错误地不拼接 IN 谓词。Mapper XML 的安全分支可生成 AND 1=0，使数据库返回空列表或零统计。这个细节很重要：如果空集合被解释成“不添加限制”，未被分配社区的员工反而会看到全库，安全属性因一个边界值而倒置。

对有 N 个授权社区的员工，XML 使用 foreach 将社区 ID 逐项绑定，形成 SQL IN (?, ?, …)。问号由数据库预编译参数承载，避免拼接可执行 SQL 文本；调用时的 ID 集合来自服务端，不由浏览器任意指定。即使前端筛选选择某社区，查询条件也必须与权限集取交集，而不能用筛选条件替代权限条件。统计页、分页的 COUNT 与 SELECT 均应使用同一范围，使总数和行数据一致。

## 6.2 列表级与对象级控制

### 6.2.1 沿业务外键反查真实社区

列表查询能通过 community_id IN 限定结果集，但修改或详情接口通常只收到 propertyId、billId、residenceId 或 buildingId。此时仅检查请求参数中附带的 communityId 会形成典型越权漏洞：攻击者可以提交“有权社区 ID + 无权房产 ID”的组合。正确路径是先用目标 ID 从真实记录出发，经 PropertyUnit→BuildingUnit→Building→Community 反查社区，再判断该社区是否在当前账号的有效范围里。账单可先由 bill_id 关联房产，居住由 residence_id 关联房产，楼栋则直接关联社区。

项目的 AccessControlMapper 和 DataScopeServiceImpl 对若干对象提供这种 requireProperty、requireBill、requireResidence、requireBuilding 类校验。其价值是把一条长期有效的安全规则放在服务层公共能力中，而不是让每个控制器凭记忆复制一段 if。写链在通过对象归属检查后仍应在事务中校验状态及版本，以防检查与更新之间发生变化。SQL 行过滤、对象反查和事务控制分别守护不同风险，不应互相替代。

假设员工仅负责社区 A，却知道社区 B 的房产 ID。如果列表已过滤但详情接口直接按 ID 查询，B 房详情仍会泄露；如果详情检查了但修改接口未检查，数据仍可能被跨社区改写。因而权限验证需要覆盖每一种可达入口，尤其是早期已有、后来并未放在新菜单上的遗留 API。Stage H-R1 的审查与修复正体现了这一点：身份分流不仅要控制用户看到哪个页面，还要封住老接口和不同角色共享组件可能带来的绕行路径。

### 6.2.2 遗留 API 与前端身份分流

前端路由能提供清楚的用户体验：管理员看到管理页，居民进入个人业务，中介只看到被许可的业务入口。但路由不是访问控制的最终执行者。浏览器可手工构造 HTTP 请求，旧的 /api/v1 路径也可能仍被外部调用。历史审查中，居民直接访问不应开放的旧房产列表获得 403，这比“居民菜单中没有房产管理”更能证明接口层封口。当页面组件复用数据时，所有网络请求仍须按当前身份选择正确 API，并由服务端重验。

权限模型的边界也应写明：本系统使用应用服务和 SQL 谓词控制多社区范围，不是 MySQL 自带的行级安全策略；也不能因抽查若干端点无越权就断言全部未来端点永久正确。新业务接口需要复用统一作用域服务、补充对象级检查和负向测试，才能保持该模型随功能增长仍然有效。

## 6.3 两个账号的可解释对照

### 6.3.1 从授权行到 72 与 168 套房

历史 Stage H-R1 验收使用两个物业工作人员对照作用域效果。staff_scope_a 对应一条有效社区授权，面向“上地西里”；staff_scope_c 对应两条有效授权，覆盖“上地西里”和“上地佳园”。同一套房产查询路径下，前者可见 72 套房，后者可见 168 套。两个返回值不是写在前端的身份标签，而是作用域记录进入 SQL 后对房产集合过滤的结果。若以全库 528 套为参照，这两个数字均是子集，说明“拥有房产查询功能”并未自然扩展为全库访问。

查询链可以逐步复核：登录账号确定账号 ID 和角色；DataScopeService 查询有效的 account_community_scope 行；Service 将社区集合传给 Mapper；XML 的 foreach 绑定社区 ID，在房产层级 JOIN 后限定 community.id；COUNT 与列表 SELECT 返回同一集合的总数和当前页；前端展示 total 与房产行。教师提问“一个人如何管两个社区”时，只看账号表中的单列是答不完整的，最有说服力的是展示两条授权行及两套账号不同的 SQL 过滤结果。

| 层次 | staff_scope_a：单社区员工 | staff_scope_c：双社区员工 |
|---|---|---|
| 有效授权关系 | 1 条 account_community_scope | 2 条 account_community_scope |
| 可见社区 | 上地西里 | 上地西里、上地佳园 |
| SQL 范围形态 | community_id IN (?) | community_id IN (?, ?) |
| 历史验收可见房产数 | 72 | 168 |
| 共同功能许可 | 可使用被授权的房产查询 | 同左 |
| 事实来源 | 最终备份授权行、Stage H-R1 测试记录 | 同左 |

这张表中的 72 与 168 是历史测试环境的验收值，不是“任何时候、任何筛选条件下”固定返回的数字。新增房产、禁用授权或改变状态筛选都会改变结果。数据库设计的成果是正确的范围关系和过滤机制，而不是为两个测试账号维护不变的页卡数字。

### 6.3.2 安全主张的合理边界

系统把四个层次接在一起：身份及功能许可、有效社区关系、列表 SQL 过滤、对象归属反查。其有效性可通过正反例检查：管理员可看其管理范围，员工只能看被授权社区，零授权员工无结果，居民访问管理员接口被拒，伪造某个社区参数不能改变目标对象真实归属。这些测试覆盖的是当前有证据的接口和场景，不能替代对所有未来接口的持续回归。

数据库账号本身的 DDL/DML 分权与最小 GRANT 尚未找到足够历史证据；本章不把应用层身份控制夸写成数据库用户级隔离。更严格的生产设计还可考虑统一授权审计、对象级策略自动校验及默认拒绝的新接口模板，但这些属于改进方向。项目现有的课程价值在于把“多小区”从页面文案落实到可查询、可约束、可测试的账号—社区关系和 Mapper 谓词。

# 第七章 关键业务数据库实现与 MyBatis 数据访问设计

## 7.1 MyBatis XML 的组织与安全参数

### 7.1.1 可复用片段与动态条件

Mapper XML 不是把 Java 拼字符串搬到配置文件里，而是把稳定 JOIN、可选筛选与结果映射显式组织起来。PropertyMapper.xml 的房产分页查询通过可复用的 FROM/WHERE 片段，使 countProperties 与 selectPropertyPage 使用相同的层级关联及过滤逻辑。若 COUNT 缺少一个状态条件，而列表 SELECT 加了这个条件，页面会显示无法翻到的“幽灵记录”；片段复用减少这类口径分叉。筛选项只有在用户提供合法条件时才进入 WHERE，范围社区则由服务端始终加入。

动态 SQL 的 choose/when/otherwise 适合处理有限枚举的排序字段或业务分支。例如数值参数可安全使用 #{pageSize} 绑定，但 SQL 的列名不能当作普通参数替换；若把客户端传入的 sortBy 直接拼到 ORDER BY，可能产生非法 SQL 或注入风险。预定义可排序列，然后由 choose 选择固定 SQL 字段，既保留列表交互，又把 SQL 结构控制在服务端。foreach 则负责把服务端计算出的社区 ID 集合转为多个绑定参数；空集合分支明确返回无行。

### 7.1.2 PreparedStatement 的问号与真实参数

当 MyBatis 日志打印 SELECT ... WHERE community_id IN (?, ?) 时，问号不是参数丢失，而是预编译 SQL 的占位符。Mapper 接收的页码、pageSize、账期和社区 ID 被分离绑定，数据库按类型处理；这样与把用户输入拼接进 SQL 文本不同。答辩时可展示 SQL 结构、参数类别与访问行数，但不应把姓名、手机号、JWT、数据库密码或文件私密路径全部打印在控制台以换取“可观察性”。

HTTP→Controller→Service→Mapper→SQL 的调用链日志服务于定位一项页面指标的来源。例如看到 /api/admin/properties 返回后，可以找到 PropertyMapper.countProperties 与 selectPropertyPage 的 MappedStatement，以及它们实际访问的层级表。日志中的 rows=20 常表示当前页查询返回了 20 行，并不证明数据库总共只有 20 套房；总量来自另一个 COUNT。可观察性要帮助解释数据库事实，而不能替代对 SQL 和数据的核验。

## 7.2 房产分页与人员居住查询

### 7.2.1 房产分页的 Count、排序与层级联查

管理端房产页面需要展示筛选后的总量、当前页房屋与所属空间信息。浏览器发出 /api/admin/properties 请求；PropertyController 校验入参和身份边界，PropertyServiceImpl 计算筛选与社区范围并调用 PropertyMapper；XML 的 countProperties 统计相同条件下的总行数，selectPropertyPage 根据排序及 LIMIT/OFFSET 取出一页。列表需要 JOIN PropertyUnit、BuildingUnit、Building、Community，才可显示社区和楼栋并用真实社区做数据范围过滤。响应把 total、page、pageSize 和当前 records 封装，前端分页组件据此展示页码。

在最终备份的 528 套房基础上，若管理员不加筛选且每页 20 条，COUNT 的业务结果应为 528，第一页 SELECT 至多返回 20 条，理论总页数为向上取整的 27 页。这里的 27 只是按“528 全部符合、pageSize=20”的数学计算，不是从某次浏览器实时请求读出的固定值；当前状态过滤、社区范围和用户搜索都可能改变 total。该例说明分页需要两条相容的 SQL：一条回答“共有多少符合条件”，另一条回答“当前给我哪些”。用当前页行数猜总量，或让前端加载全部行再切片，都无法正确表达作用域下的真实结果。

安全的参数传递同样影响分页。pageSize 应限制在服务端可接受区间，OFFSET 由可信 page 与 pageSize 计算，排序列只能在预设集合内选择，contains 搜索使用绑定参数并处理通配语义。分页查询的 JOIN 还可能因一房多住户而重复房屋行，因此主列表应谨慎选择一对一的空间层级作为骨架，把当前业主和住户详情通过独立查询或聚合映射补充。模型拆表换来历史性，也要求查询设计尊重基数。

### 7.2.2 人员与居住不是直接扫 Person

住户页面的一行通常不仅含 Person 姓名，还要说明其居住房产、社区、房号及入住状态。直接 SELECT person 无法回答“住在何处”，也可能把尚未建立有效居住关系的人误算为当前住户。ResidentMapper.xml 从 Residence 出发，关联 Person 和 PropertyUnit，再经 BuildingUnit、Building、Community 得到位置，按状态、搜索词及账号可见社区过滤，分别执行 countResidents 与 selectResidentPage。最终 606 人与 597 条 Residence 数量不同，也提醒不能把“人员总数”直接当作“住户关系数”。

同一个人可能有历史居住记录，Residence 的一行对应一次具体居住事实。详情页如果需要展示多段历史，不应只取一个 Person 的静态房号；相反，应沿关系表按时间与状态查询。列表页若只展示当前住户，必须明确 WHERE 的当前条件。这样，一个搬出操作是结束一段 Residence 并改变相关房产状态，而不是从 Person 删除姓名。该查询代价是更多 JOIN，但它与模型的现实语义一致。

## 7.3 账单、统计与 Dashboard

### 7.3.1 账单明细与付款回查

账单列表与详情承担不同问题。BillMapper.countBills/selectBillPage 处理账期、状态、小区和搜索条件，单行可显示账单级财务汇总；详情再分别查询 BillItem 和 Payment，使读者能看到应收由哪些项目组成、实收来自哪些成功付款。如果把两组一对多明细一次性直接 JOIN 进列表，会遇到第五章讨论的乘法重复，也会使分页以“账单项×付款”中间行而不是账单计数。先确定账单主集合，再查询明细，是正确性与页面性能共同要求。

FeeType 和 FeeStandard 的拆分允许解释项目名称和定价依据，BillItem 的快照避免旧账单因费标变化而变动。财务 View 提供账单级应收、实收、欠费的共同口径，账单页与 Dashboard 可复用这套定义。即使某账单没有成功付款，LEFT JOIN 仍让它以“实收 0、欠费等于应收”出现。相反，失败付款记录可以在付款明细中保留历史，但不计入已收指标。页面“金额正确”不能仅凭一个显示数证明，必须能从账单项与付款行手算回去。

### 7.3.2 Dashboard 与月年报表各自承担什么

Dashboard 是多个指标的组合展示，而非一张预先写死的总表。DashboardView.vue 发出 overview、monthly-collection、fee-composition、bill-status、occupancy、overdue-top、residence、rentals 等请求；后端分别由 DashboardServiceImpl 及统计服务调用 DashboardMapper.xml、StatisticsMapper.xml 的语句。课程展示可选择四个指标深入追踪：overview 结合房产和收费概况；monthly-collection 汇总指定账期的应收与成功实收；fee-composition 按费用类型解释应收构成；occupancy 从房产与有效居住事实计算占用。它们底表、JOIN 和时间口径不同，不能说“Dashboard 数据来自某一个 SQL”。

年度统计沿真实账单月份聚合，月度统计可下钻到社区再到明细。若某个月数据库根本没有账单，后端不会凭日期制造这一月的金额；前端为年度视觉完整性显示 1—12 月刻度，但指标为 null。对单社区工作人员，统计 SQL 必须重聚合有权社区的数据，不能直接使用全局汇总。收费类型分布若按 BillItem 聚合，应收口径与 SUCCESS Payment 的账单级实收不能未经分摊就混称为“每类费用实收”。将每个图表的事实粒度说明清楚，比多做一张图更重要。

## 7.4 写链路：入住、通知与车证

### 7.4.1 入住与搬出：人房关系和房产状态一致性

办理入住需要核验房产是否可入住、人员与房产关系是否合法、是否已有冲突的有效 Residence，然后插入新的居住事实并调整 PropertyUnit 的占用状态与 version。Service 的 @Transactional 将属于同一次办理的数据库写入置于共同边界；Mapper 用带状态或 version 条件的 UPDATE 防止两个请求都在旧状态下“成功”。若其中一步违反 CHECK 或唯一键，异常应使本次事务内已执行的写入回滚，客户端收到可理解的失败响应，而不是遗留“已入住但房产仍空置”的半成品。

搬出是结束某段居住关系并重新评估房屋占用状态，不等同于删除 Person。即使当前住户搬走，他之前的付款、通知及居住历史仍需引用稳定人员记录。2026-08-30 的真实失败证明数据库 CHECK 并非纸面规则；历史双请求 200/409 冲突证明应用状态检查和版本控制对并发有意义。两例的输入与结论在第九章按时间线展开，并区分“一个 HTTP 请求内部原子性”与“跨多个独立请求的完整业务流程”。

### 7.4.2 通知发送的 N:M 展开与欠费口径

通知发送首先创建 Notification 主记录，再将目标范围解析为具体 Person，写入多条 NotificationRecipient。这样一条消息可有多个收件人，每个收件人可独立记录 TO/CC、投递状态和 read_at；若这些字段存在 Notification 主表，一条通知最多只会有一种已读状态，与实际不符。V5 增加接收人 payload_json，使账单提醒可以在每个接收关系上携带个性化内容，仍由主外键维持人和通知的身份关系。

欠费通知尤其需要共享财务口径。若通知服务用一套“应收减去所有付款”公式，而 Dashboard 用只计算 SUCCESS Payment 的 View，同一用户在页面与通知里会看到不同的欠费。现有 ChargeNoticeComposer 通过批量 selectDueRows 等链路收集目标，减少逐人查询，且应把每人欠费与账单级汇总区分。由于付款没有费用项目级分摊，通知不能推断“该用户水费仍欠多少”并伪装为精确项目结论。最终快照的 7 条通知与 507 条收件关系，可作为 N:M 联系表已被实际使用的结构证据。

### 7.4.3 车证申请到审核发证

车证流程不是在 vehicle 表中加一个“已审批”布尔值。车辆身份、申请记录和正式许可各有不同的生命周期：居民发起申请时形成待审事实，物业在其范围内审核，获批后才形成许可。ParkingPermitMapper 对人、房产或申请状态执行查验，审核路径使用锁或条件更新，避免同一待审申请被重复处理。空间归属和申请资格仍需从真实 Person—Residence/Ownership—PropertyUnit 关系核验，不能以用户填写的社区名为准。

最终演示数据有少量车辆、申请和许可证，说明审批链存在可核验样例；但 parking_space 和 parking_right 为空，故报告不把“车证发放”写成“车位资源调度、占用和收费已完成”。这是一种粒度边界：许可证明人车与审核结果，车位则是另一类物理资源，不应由于名称都含“停车”而混为同一事实。

## 7.5 文件、地图与表计：作为数据库设计的外延

### 7.5.1 户型图对象与关系元数据

户型图上传时，新对象先写入 MinIO，随后在 MySQL 写 file_object 与对应业务关联；替换旧图时，数据库事务提交后再删除旧对象，若数据库写入失败则尝试清理新对象。这个顺序优先避免“旧对象先删、数据库又回滚”的不可恢复显示错误。它仍不是跨 MySQL 与 MinIO 的原子事务：删除补偿也可能失败，留下孤儿对象，需要后续对账和清理机制。数据库表保存 bucket、key、内容类型和校验值，使应用能从房产或模板定位图纸；MinIO 只负责字节存放，不负责业务外键。

户型图选择有房产专属、布局面积变体、默认模板等优先级。共享默认图减少重复对象存储，具体房产需要不同图时再覆盖。Stage 1 Docker 数据迁移从冷备份经临时同版本 MinIO 和 mc mirror 转到目标服务，最终抽样核对对象与 MySQL file_object 行；该历史过程证明了至少这一批数据的可恢复性，同时也暴露出跨存储恢复必须以键对账，不能只恢复一个 volume。

### 7.5.2 地图坐标落库与表计时序

地图页面的社区和楼栋点位来自 MySQL 中已保存的经纬度及社区范围数据；高德 Web Service 用于定位补全，前端高德 JS API 用于底图显示。真正值得写入数据库报告的是空间对象如何与业务层级关联，以及点位如何在页面查询中与楼栋、房产数量配合。项目不使用 MySQL POINT 和空间索引实现邻近检索，因此地图不应被包装为 GIS 数据库实验；高德服务认证和地图白屏属于系统集成经验，正文只需保留与持久化坐标有关的部分。

表计模拟器面向当前 meter 状态写入 meter_reading，依赖表计与时刻唯一键保证重复执行不会无限造出相同读数。历史验收中第一次插入 1584 条、第二次 0 条，解释了“幂等写入”如何通过键与 INSERT IGNORE 配合实现。此处仍要区分：模拟器验证关系模式和接口，不能代替真实设备时钟、重传顺序、异常读数治理与长期采集系统。

# 第八章 数据库演进、Flyway 版本管理与数据生命周期

## 8.1 为什么数据库需要自己的版本历史

当数据库只有几条可丢弃测试行时，改一列后删表重建看似省事；项目进入 528 套房、数千账单及图纸元数据阶段后，这种方法会同时抹去既有人员、资金和历史关系。Git 能保存 Java、Vue 和 SQL 文件每次提交的文本，但不能自动说明某个运行中的 MySQL 数据库已经执行过哪些 DDL，也不能把数据库的现有业务行安全地“切回”某个代码提交。Flyway 的作用是在数据库内记录已应用版本，并按顺序执行尚未应用的迁移，使源文件变化与库结构变化形成可核查的对应。

版本管理不是为报告增加一个技术名词，而是对长期演化风险的回应。新增车证功能需要关系表和约束；新增多小区员工范围需要 account_community_scope；查询变慢可能需要补索引。若这些改变只在开发者电脑上手工点执行，其他环境即使拉取同一代码，也可能缺表、缺列或有不同唯一规则。迁移文件将“做了什么、顺序如何、已经执行到哪一版”转成共享材料。项目的 V1—V10 展示了这一方法，也因最终结构存在来源缺口，提供了检验迁移纪律是否完整的反面素材。

### 8.1.1 V1–V3：基础模式、参考数据与安全/文件扩展

V1 建立物业业务的基础关系模式，包含空间资产、人房、租赁、收费、表计和部分停车、通知相关结构；同阶段的 seed 断言与负向约束测试说明设计并非只画 ER 图。V2 加入稳定的参考数据，让费用、类型或状态基础表在页面查询中有可用的分类值。V3 在已有模型上补账号/角色、文件对象与户型图相关结构，使应用开始从“数据库原型”进入可登录、可访问文件的系统形态。V3 还曾对当前产权施加比最终库更严格的规则，表明迁移记录既是历史证据，也可能被后续真实设计修正。

这三版的顺序有因果：先确定可引用的业务主键和外键，再提供参考行，最后让身份与文件关联有稳定的目标对象。若倒序处理，文件元数据无法可靠引用房产，权限也无社区对象可限定。第一版规模较大并非后续每版都要大改；相反，成熟后应使每次迁移围绕清楚的新需求和风险最小化。

### 8.1.2 V4–V6：多小区、通知与索引

V4 增加 account_community_scope 等授权结构，把教师后来关注的“一个账号管理多个小区”落实为 N:M 关系，也增加空间边界和通知接收关系相关结构。通知主表与接收表的出现使“按人已读”可表达，但 V4 文件对 notification 有 ALTER 依赖，而在当前可见 V1—V3 中未找到相应初建语句；这属于迁移链需要如实说明的缺口。V5 为 notification_recipient 增加 payload_json，回应对每个收件人保存个性化通知内容的需求。新增的是联系实体上的载荷，而不是把整个通知体系改成 JSON。

V6 增加 idx_bill_period_status，是一版以实际查询模式为依据的物理设计改动。已有同房同账期唯一键负责防重，不能很好服务跨房产的账期、状态过滤；新增 year、month、status、bill_id 顺序的索引后，历史代表性计划的检查行数和耗时下降。这个例子说明数据库演进不只为增加表、字段，也可回应统计查询的性能问题。它与第七章的页面→SQL 链合在一起，构成“需求—查询—索引—验证”的完整故事。

### 8.1.3 V7–V10：居住、车证与户型图变体

V7 扩展居住预计结束日期，并新增居民报事事件，使“住多久”和“报修了什么”不被塞进 Residence 的单个状态列。V8 加入停车资格、申请和许可相关表，承接居民申请、物业审核、正式发证的分阶段模型；该迁移还包含少量演示 INSERT，提示迁移文件中结构变更与样例数据耦合的维护风险。V9 把户型默认图关联纳入模式，V10 进一步增加面积变体，让相同户型、不同面积的资源可以分层复用。后两版都不是“每套房复制一张图”，而是在实体与共享模板之间建立选择关系。

## 8.2 迁移来源缺口与兼容反思

### 8.2.1 最终数据库与 V1–V10 不能画等号

2026-09-01 的最终备份验证了 46 张业务表、flyway_schema_history 表以及两个财务 View；当前可见 V1—V10 迁移能明确创建其中 44 张业务表。agency_staff 与 notification 的初建语句、两个财务 View 的初建语句，以及若干最终生成列和产权规则的变更原文，尚未在这组版本文件中定位。V4 对 notification 的 ALTER 还直接表明它假设该表先前存在。因而可以说最终数据库具备这些结构，也可以说 Flyway 历史表记录 V1—V10，但不能宣称“拿十个当前迁移脚本接到空 MySQL 就能无差异建立最终库”。

这不是否认 Flyway 的价值，而是说明工具不能代替执行纪律。只要存在绕开迁移的手工 DDL、丢失的脚本或不同分支的历史，数据库可能与源文件偏离。课程报告应把最终快照作为现状证据，把迁移文件作为可见演进证据，并对两者间缺口设置修复路径：整理真实来源、用结构差异核对版本、为后续变更统一补齐迁移和测试。在未查清原始变更 SQL 之前，不应为了让故事完整而虚构某一版本号或擅自改写历史迁移。

### 8.2.2 字段长度、既有数据与变更纪律

有数据的库上添加 NOT NULL，必须先考虑旧行如何获得非空值；添加 UNIQUE，必须先扫描重复数据；添加 FK，要检查孤儿行；添加 CHECK，要检查历史输入是否违反新规则；缩短字段长度，要考虑截断与字符集；建索引会占用存储并影响写入。这些风险解释了为什么“在本机执行一大段 SQL”虽然快捷，却不足以替代可核验的迁移流程。每次结构变更应记录前置数据检查、DDL、可能的数据修复和上线后的验证查询。

教师讨论中曾提到字段表达能力扩展，但当前可见证据尚未定位具体“32→64”字段、原报错和对应变更语句。[待核验] 因此本稿只从一般性兼容原则解释字段长度变化，不把这一口述写成已经查明的项目故障。与之相比，V6 索引、V8 车证和 V9/V10 户型变体均有明确脚本，能够写成实证演进。把证据强弱分开，是数据库版本管理报告本身的一部分。

## 8.3 备份、恢复与容器数据生命周期

### 8.3.1 MySQL 与 MinIO 的恢复对账

PUBLIC_DEMO Stage 1 并非通过清空新库随意造一批数据，而是从部署前 MySQL 备份恢复 community_db，并迁移 MinIO 的 property-assets 对象。MySQL 使用 binary-safe 的文件复制和容器内 client 导入，随后检查业务表、行数、Flyway V1—V10 历史、两个 View、约束与索引，并抽查真实中文数据和字符集。这些核验比“mysql 容器 healthy”更接近数据库是否真正可用：容器存活只能说明进程在运行，不能证明账单、住户、视图和中文没有丢失或乱码。

MinIO 迁移经过冷备份、可写工作副本、同版本临时服务、mc mirror 再到目标实例，恢复后对对象总数、样本键与 MySQL file_object 做抽样对应。最终恢复验证记录了 12 个对象；这与表中图纸关系数量不能简单相加，因为多个模板或变体关联可能复用同一个对象，且对象元数据与业务关系不是一对一固定公式。Redis 没有迁移旧数据，测试以 redis-cli PING 得到 PONG 证明运行可达；它属于可重建运行状态，不与 MySQL 的业务事实和 MinIO 文件采用同一恢复策略。

| 对象 | 恢复/验证方法 | 已记录的结果 | 证明范围 |
|---|---|---|---|
| MySQL community_db | 备份导入；表、行数、约束、View、中文抽查 | 业务表、V1—V10 历史、2 View 可用 | 该备份在当时环境可恢复 |
| MinIO property-assets | 同版本临时服务、mc mirror、对象键抽查 | 12 个对象及样本元数据关联 | 该批对象可迁移、可对账 |
| Redis | 新实例 PING | PONG | 服务可达；不证明旧缓存已迁移 |
| 数据卷 | Compose down 不带 -v 后再 up | MySQL/MinIO 关键数据仍在 | 容器生命周期与卷生命周期分离 |

### 8.3.2 down/up 持久化与权限边界

Docker 容器可被删除和重建，named volume 则有独立生命周期。Stage 1 在完成恢复后执行 docker compose down（明确不加 -v），再 up -d，并复查 MySQL 业务数据和 MinIO 对象仍存在。若只验证第一次启动正常，无法排除数据其实写在容器临时层里，一次重建即丢失；down/up 实验为“数据生命周期不依赖容器进程”提供直接证据。此验证不等于异地灾备或长期自动备份轮转，仍需保存独立备份并定期练习恢复。

Docker 内部连接使用 mysql:3306、redis:6379、minio:9000 等服务名，宿主机调试端口另有映射。网络通畅和健康检查只证明运行链可建立，不自动保证业务授权。应用连接 MySQL 的账号存在，但尚未找到实际 SHOW GRANTS 或独立 DDL/DML 账号分权的完整历史证据，因此不能把 Compose 中的用户名配置写成已验证的最小数据库权限。部署对数据库报告的价值，主要在于可重复恢复、跨存储对账与持久化边界，而不在于容器技术本身。

# 第九章 系统测试、数据库验证与性能分析

## 9.1 数据库结构与负向约束

### 9.1.1 V1 的 16 个负例与 14 个 seed 断言

正向种子数据能够说明模型允许一批合法输入，却不能证明非法输入会被挡住。项目 V1 的 database/tests/03_constraint_negative_cases.sql 设计 NEG-01—NEG-16，覆盖重复业务编码、缺失层级父对象、非法人房日期、授权组合、孤儿账单项、设施规则、授权与房产错配及重复合同等情况；初期 evidence 记录了 16 个预期失败与 A01—A14 的种子断言通过。负例的结果不是“测试失败”，而是数据库按预期拒绝坏数据。它们为 PK、FK、UNIQUE、CHECK 和复合 FK 的设计理由提供直接实验支撑。

以五类输入为例，空间父对象不存在时，房产不能静默变成无法定位社区的孤儿；重复层级代码会被业务唯一键拒绝；产权或居住日期颠倒时，CHECK 避免历史时间线自相矛盾；BillItem 引用不存在的 Bill 会被 FK 拒绝；授权房产与挂牌房产不一致时，复合外键阻断“每个 ID 单独存在、组合却错误”的情况。测试方法是在可控初期数据库中逐条提交违规 SQL，并检查对应错误、回滚测试数据，再执行正向断言。最终项目继续扩展后的约束数量不能只凭 V1 测试概括为“全部被覆盖”，负例证明的是这些特定规则。

| 用例类别 | 代表负例 | 预期数据库反应 | 对应设计主张 |
|---|---|---|---|
| 业务唯一 | NEG-01～03 中的重复层级标识 | 拒绝重复 | 技术主键之外还需自然业务键 |
| 层级参照 | NEG-04～06 缺失父对象 | FK 拒绝 | 房屋不能脱离真实社区层级 |
| 时间边界 | NEG-08～09 不合法人房日期 | CHECK/规则拒绝 | 历史关系的起止顺序需一致 |
| 账务参照 | NEG-12 孤儿账单项 | FK 拒绝 | 项目依附于真实账单 |
| 组合参照 | NEG-15 授权与房产错配 | 复合 FK 拒绝 | “各 ID 存在”不代表“组合合法” |
| 业务重复 | NEG-16 重复合同 | 唯一/业务规则拒绝 | 同一业务合同不应重复记账 |

### 9.1.2 最终 Schema 的视图与约束核验

部署恢复时，验证不能只统计表数，还要检查 View、外键、CHECK、索引及字符集。历史 Stage 1 Runbook 核对最终 46 张业务表、Flyway 历史和两个财务 View，记录了外键与 CHECK 的整体清单，并抽查中文数据。导出文件中 View 在前部有用于导出依赖顺序的临时占位定义，实际定义应在最终结构段核对；否则可能误判“View 只是 SELECT 常数”。恢复后还需用典型查询验证它们能基于账单和付款返回真实聚合，而不只是 information_schema 中有视图名字。

这一检查还揭示了迁移文件与最终库的差异：最终结构真实存在并可运行，并不意味着全部由当前可见 V1—V10 脚本生成。报告将初期约束测试、最终备份审计和恢复验证分别定位到自己的时间点，不把 2026-08-21 的 V1 负例自动说成对 2026-09-01 全部约束的回归覆盖。

## 9.2 事务、一致性与并发

### 9.2.1 2026-08-30 的 CHECK 失败与回滚

2026-08-30 的一次真实办理过程提供了比示意代码更具体的事务证据：用户先通过独立请求创建 Person，得到成功响应；随后执行入住流程，流程内部涉及资格或停车相关数据写入，其中一步触发 MySQL CHECK 3819，导致这次办理请求失败。日志与事务核对显示，属于该入住事务的多步写入未以“前半成功、后半失败”的半完成状态保留。该例说明约束与事务并非二选一：CHECK 识别非法行，事务负责在整项业务动作失败时撤回已做的相关更改。

必须准确划定原子性边界。先前独立创建的人员记录并没有被后一次入住请求回滚，因为它们不是同一个数据库事务，也不是同一个 HTTP 请求；若报告说“整条从创建人到入住的链全部回滚”，就与日志不符。开发上的教训是：业务界面看似一个连续流程，服务端可能由多个请求组成。要保证哪一段“要么全部成功、要么全部失败”，需在代码中明确事务起止，而不是依据页面步骤想象事务边界。

| 时间顺序 | 可观察事件 | 数据库后果与解释 |
|---|---|---|
| 先前请求 | 创建 Person 返回 200 | 独立提交；不在后续入住事务内 |
| 入住请求开始 | 校验并执行多项写入 | 这些操作受入住服务事务约束 |
| 中间步骤 | MySQL CHECK 3819 | 非法状态被数据库拒绝 |
| 事务结束 | 入住请求失败并回滚 | 本次办理不留半完成关系与状态 |

### 9.2.2 双人入住冲突与车证审核锁

事务能保证一次请求内部一致，却不能仅凭“先查空房、再插入”防止两个请求同时看到旧状态。Stage H 的历史并发验收对同一 property 452 发出两个办理尝试，结果一个成功返回 200，另一个因状态或版本冲突返回 409；后续搬出后，房产 version 从 0 变化到 2，未留下两条冲突的当前居住。这里的 409 不是普通页面报错，而是“另一个操作者已经改变目标状态，请重新读取”的并发语义。数据库当前态唯一约束、条件更新与服务端事务共同防止双成功。

车证审核路径同样涉及“待审只能被处理一次”。Mapper 对相关人房资格或申请行使用锁定查询和条件更新，避免两个物业人员同时发证。课程报告不将这些局部控制泛化为完整串行化隔离实验，也不声称所有并发场景已经覆盖；它们展示了针对具体状态竞争选择事务、锁或乐观版本的必要性。未来若扩展批量审批，还需定义锁顺序、超时处理和重试策略。

## 9.3 权限和统计正确性

### 9.3.1 社区 Scope 的正反例

权限测试的目标不是证明员工“能登录”，而是证明同一个查询因有效授权关系不同返回不同社区集合。历史 staff_scope_a 与 staff_scope_c 验收分别得到 72 与 168 套房；对照最终备份的授权行和 Mapper 的社区 IN 谓词，可把差异解释为一社区与两社区的范围变化。另需检查零授权时无行、对象级访问无权 ID 被拒、居民访问管理端接口为 403。这些反例使 DataScope 的主张从“写了一个服务类”变成可观察的授权边界。

测试还应固定角色、社区授权状态、过滤条件与数据库快照。若一个员工后来被增加社区，或房产状态变化，72/168 的具体数字会变；不能把历史验收值当永久常量。对安全来说，更重要的断言是结果中每个房产都能沿外键追到允许社区，且 COUNT 与页面行的范围相同。负向测试可用已知属于其他社区的 propertyId 直接调用详情与修改接口，而非只看列表是否过滤。

### 9.3.2 财务手算与无记录语义

财务正确性需要从底表回算，而不只是比较 Dashboard 与月报两个可能共用错误 SQL 的页面。核对一张账单时，先求 BillItem.amount 的和，再仅求 status=SUCCESS 的 Payment.amount 之和，最后计算 max(应收－实收,0)，与 v_bill_financial_summary 一行比较；核对一个月时，对该账期所有账单行再次求和，用实收÷应收×100 与月度统计比较。若有无付款账单，必须确认它仍在结果中。第五章的演示计算给出了三种边界输入，实际核对必须取同一备份时点的数据。

年度页面还有另一类容易忽略的错误：“缺月”和“零元”不能同义。没有任何 Bill 的月份，SQL 不产生该组结果，前端补齐月份标签时指标保持 null；若存在 0 元账单，该组应有账单数和零金额，收缴率是否可定义还受 NULLIF 分母规则影响。统计图准确与否，不仅取决于数值计算，还取决于缺失数据的语义。教师曾要求解释图表数字的产生，项目通过运行日志定位请求，再追到 Mapper XML 的 JOIN、LEFT JOIN、聚合和 View；这条核验路径比截图本身更有说服力。

## 9.4 数据规模、索引与恢复

### 9.4.1 演示数据的结构真实性与边界

最终快照中，4 小区—14 楼—40 单元—528 房构成完整空间层级；528 房与 1584 表计、3696 张账单形成规则化一对多；账单再关联 18273 条项目和 3324 条付款，通知与 507 条收件关系形成另一组联系。这一规模比几十行随意样例更能暴露分页、JOIN、聚合和权限范围过滤问题。它又明显显示脚本化结构生成特征，完整的 528 房批量生成器未在现存文件中找到，[待核验] 因此不写具体生成算法，也不把数据称为真实生产运营记录。

最终空表需要单列说明：lease_contract、contract_participation、parking_space、parking_right、spatial_boundary、facility_placement、property_floor_plan、account_agency_role 均无最终演示行。V1 初期 seed 曾对其中部分关系做正向断言，说明它们在早期样例中被验证过；但不能用旧 seed 证明最终 PUBLIC_DEMO 库含有合同签约和车位占用场景。数据规模与功能覆盖是两个维度，报告的实证范围应随最终快照而不是随表名扩大。

### 9.4.2 代表性索引的执行计划

性能测试首先固定 SQL 的 WHERE、JOIN 和排序，再比较不同访问路径。V6 的代表性账单查询原先利用不到以 property_unit_id 领先的唯一键来高效限定跨房产账期；新增以 billing_year、billing_month、status 为前缀的索引后，历史 EXPLAIN ANALYZE 的检查行数约从 603 降到 11，耗时约从 0.85 ms 降到 0.13 ms。这里的主要证据是计划访问路径与检查行数变化，毫秒级时间受环境噪声影响更大。

测试规模约为 3696 张账单，足以展示索引列序对这类查询的影响，但还不足以推断百万账单时的最优方案。不同月份账单分布、员工社区范围、返回列及冷热缓存都会改变优化器选择。下一阶段应针对真实慢查询保留 SQL、参数、EXPLAIN 和代表性数据分布，并关注新索引的写入成本；本报告只给出已记录的样本结论。

### 9.4.3 恢复、压力场景与可观测追踪

Docker Stage 1 的 down/up 验证了数据卷与容器生命周期分离，MySQL 中文数据、View、约束及 MinIO 样本对象仍可核对；Stage 2 验证应用、数据库和文件服务之间的内部连接及 HTTP 基本链路。压力脚本的历史短时场景记录约 50 个虚拟用户和特定请求集合，结果如系统场景 1016/1016、数据库场景 945/945 成功，只能说明当时这组脚本与环境没有观察到请求失败，不能换算成长期生产容量或证明所有复杂查询都足够快。

可观测链把 HTTP 方法与路径、用户、Controller、Service、Mapper、压缩 SQL、耗时和状态关联，用于答辩现场从页面图表追到底表。它仍需谨慎处理日志口径：同一运行会话与历史会话不得混合，敏感个人信息和凭据不得因调试输出。Stage 2.6 的 Run Session 分类修复说明观测证据本身也要有清晰边界。最终验证结论应由 SQL/备份、实际 HTTP 响应、日志和页面共同支撑，而非由单一“PASS”标签代替过程。

# 第十章 总结、设计反思与后续改进

## 10.1 数据库设计成果

### 10.1.1 从现实规则到可验证关系模式

项目最重要的成果不是组合 Spring Boot、Vue、MySQL 等技术名称，而是将现实中不断变化的物业事实拆分为具有清晰身份和联系的关系模式。空间层级让房产归属可追溯；Ownership 与 Residence 分离，使业主、住户和历史不再互相覆盖；账单、账单项与付款分离，使应收与实收能够从底表复核；NotificationRecipient 和 account_community_scope 将具有独立属性的 N:M 联系实体化。这些结构由外键、业务唯一键、CHECK 和事务守住最基本的一致性，再通过 Mapper SQL、View 和页面指标投入使用。

数据库课程设计的论证应当回到“为什么”。把当前业主直接写在房屋一列，难以保留产权变动和共享份额；把已收直接写在 Bill 一列，难以核对多次付款；把一个 community_id 放在账号一列，无法表达同一工作人员管理多个小区；用 INNER JOIN 从付款出发做欠费统计，会漏掉最需要被看到的未付款账单。每一个看似复杂的联系表或 LEFT JOIN，都对应一个更简单方案会产生的具体错误。项目通过最终结构、历史负例和运行日志，至少为这些核心设计提供了可检验依据。

## 10.2 对长期演进与系统边界的认识

### 10.2.1 已发现的问题应成为改进路径

当数据库有大量关联数据后，Schema 不再是随意清空重建的开发附件。Flyway V1—V10 展示了需求驱动的演化：从基础关系到多社区授权、通知逐人信息、账期索引、车证和户型图变体。与此同时，最终备份与现存迁移文件并非完全同构，说明“引入迁移工具”只是起点，真正有效的是所有结构修改都进入同一条审查与回放链。下一步应先整理缺失的历史 DDL 来源，建立最终 Schema 差异核验和从备份恢复的定期演练，而不是补造一个看似完美的历史。

其他边界同样值得明确。MySQL 与 MinIO 的文件操作没有分布式原子性，需要孤儿对象扫描和补偿记录；深 OFFSET 分页在更大规模下仍可能代价高；部分表存在但最终演示库没有业务行；付款只到账单级，无法进行费用项目级精确分摊；当前地图不是 MySQL GIS；Redis 可用性检测不等于已验证缓存收益。课程设计不是生产交付承诺，把这些限制讲清楚，反而使已经验证的关系模型、事务和恢复成果更可信。

## 10.3 答辩与正式成稿的证据纪律

### 10.3.1 不把技术名词替代数据库论证

正式报告和课堂演示应选几条能讲到底的链：一条产权或居住现实规则，对应一段 ER 与唯一约束；一张账单的项目、付款和 LEFT JOIN View，能手算出报表金额；一个工作人员的 scope 行，能解释房产列表和对象级拒绝；一条历史 CHECK 失败，能说明事务回滚边界；一条 V6 查询，能读懂前后执行计划。这样回答教师的问题时，页面、代码、SQL、日志和数据相互指向，而不是停留在系统截图或技术栈图。

本稿仍需排版、图表截图与参考文献规范化。正文中的事实根据源码、最终备份和历史记录分时点叙述；演示计算已明示非实际账单；少数确实找不到的生成器与迁移来源保留待核验标记。后续若取得原始手工 SQL、备份差异或真实账单核对样本，可以在不改变十章结构的前提下替换相应占位与补强证据。报告的完成标准不是没有任何未知，而是读者能清楚区分已实现、已验证、合理解释和仍待追溯的部分。
